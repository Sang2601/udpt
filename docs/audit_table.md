# Bảng Đối Chiếu Hiện Trạng và Giải Pháp Nâng Cấp Hệ Phân Tán
## Dự Án: PhenikaaHotel - Báo Cáo Môn Ứng Dụng Phân Tán

| Bài Học | Nội Dung Lý Thuyết Theo Bài Giảng | Hiện Trạng Dự Án Ban Đầu | Thiếu Gì | Cách Bổ Sung & Triển Khai Thực Tế | Cách Kiểm Chứng Thực Nghiệm |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Bài 1: Tổng quan hệ phân tán** | - Mô hình Client–Server, phân tầng (N-tier).<br>- Trong suốt truy cập, vị trí, sao lặp, lỗi.<br>- Tính mở qua IDL/API contract.<br>- Co giãn (chiều dọc, chiều ngang, replica).<br>- Chia sẻ tài nguyên & giới hạn vật lý. | - 1 tiến trình monolithic Express `server/server.js` chạy 5 cổng giả lập.<br>- Dùng chung 1 file SQLite cục bộ `hotelbooking.sqlite`.<br>- Frontend tự giữ mảng các cổng và luân chuyển khi lỗi.<br>- Không có database phân tán thực. | - Thiếu kiến trúc microservice thực thụ.<br>- Thiếu API Gateway chuẩn hóa ranh giới.<br>- Thiếu cơ chế sao lặp và phân tán dữ liệu thực tế.<br>- Client vi phạm nguyên tắc phân tầng khi tự biết port của server. | - Tách thành 4 microservices độc lập: `Auth`, `Hotel`, `Booking`, `Notification`.<br>- Xây dựng `API Gateway` tại cổng 5000: định tuyến, `X-Request-Id`, timeout 10s, load balancer phân phối traffic cho Booking Service.<br>- Triển khai cụm CockroachDB 3 node (`roach1`, `roach2`, `roach3`) phân tán bằng Raft consensus qua Docker Compose. | - Chạy `npm test` kiểm tra tính toàn vẹn hệ thống.<br>- Chạy `curl http://localhost:5000/gateway/status` xem cấu hình định tuyến và trạng thái các node replica.<br>- Chạy `docker compose up -d` kiểm tra cluster 3 node bằng `roach-init`. |
| **Bài 2: Tiến trình và luồng** | - Tiến trình vs Luồng (không gian bộ nhớ riêng vs dùng chung).<br>- Node.js Event Loop, I/O bất đồng bộ vs CPU-bound tasks.<br>- Mô hình Dispatcher và Worker Pool có giới hạn (bounded queue).<br>- Tránh thread exhaustion, tránh thread-per-connection. | - Chỉ dùng Express async/await đơn luồng.<br>- Quảng cáo "đa luồng" nhưng thực chất chỉ là async I/O của Event Loop.<br>- Tính toán báo cáo admin chạy trực tiếp trên luồng chính, gây nghẽn Event Loop khi tải lớn. | - Không có luồng worker thực sự để xử lý tác vụ nặng.<br>- Không có cơ chế quản lý vòng đời luồng, PID, ThreadId, JobId.<br>- Thiếu cơ chế backpressure (hàng đợi hữu hạn). | - Xây dựng `WorkerPool` sử dụng module chuẩn `worker_threads` của Node.js trong `services/booking`.<br>- Pool kích thước cố định (4 worker), hàng đợi giới hạn (50 jobs).<br>- Tác vụ tổng hợp báo cáo (`reportWorker.js`) tính toán chỉ số thống kê, doanh thu, công suất phòng được chuyển sang worker thread.<br>- Log rõ PID, ThreadId, JobId. | - Chạy kiểm thử tự động `tests/worker_pool.test.js`.<br>- Kiểm chứng log hiển thị `ThreadId` khác nhau trên cùng PID.<br>- Kiểm tra trường hợp hàng đợi vượt ngưỡng (queue saturation) trả về lỗi quá tải có kiểm soát (429/503). |
| **Bài 3: Trao đổi thông tin** | - Giao thức tầng vận chuyển TCP/UDP.<br>- Remote Procedure Call (RPC): client stub, server stub, marshalling, unmarshalling, JSON-RPC 2.0.<br>- Message-Oriented Middleware (MOM): Queue, Pub/Sub, RabbitMQ.<br>- Transactional Outbox pattern chống mất thông điệp. | - Chỉ có REST HTTP nội bộ tự chế.<br>- Không có RPC giữa các service.<br>- Không có message broker, không có sự kiện bất đồng bộ.<br>- Đơn đặt phòng và thông báo được ghi đồng thời trong 1 tiến trình. | - Thiếu giao tiếp RPC chuẩn giữa các service nội bộ.<br>- Thiếu Message Broker để tách rời bên gửi và bên nhận.<br>- Nguy cơ mất thông báo nếu server crash giữa chừng. | - Triển khai chuẩn `JSON-RPC 2.0` qua HTTP giữa Booking Service (client stub) và Hotel Service (server stub) để lấy giá niêm yết có thẩm quyền (`hotel.getRoomTypeRate`).<br>- Triển khai `RabbitMQ` với durable queue `notification.bookings.queue`, persistent message và manual ACK.<br>- Áp dụng `Transactional Outbox` tại Booking Service: lưu sự kiện vào bảng `outbox_events` cùng giao dịch đặt phòng, tiến trình nền tự động publish khi RabbitMQ sẵn sàng. | - Chạy `tests/json_rpc.test.js` xác nhận chuẩn JSON-RPC 2.0, mã lỗi `-32601`, `-32001` và timeout.<br>- Kiểm tra outbox lưu trữ an toàn khi RabbitMQ tạm tắt và gửi lại thành công khi RabbitMQ online.<br>- Kiểm tra thông báo lưu vào in-app notification. |
| **Bài 4: Định danh** | - Thực thể, tên, địa chỉ, định danh (Identifier).<br>- Không gian phẳng vs có cấu trúc (DNS).<br>- Bảng băm phân tán (DHT) và giải thuật Chord ($m$ bit, successor, predecessor, finger table, routing hops).<br>- Di chuyển khóa khi thêm/bớt node (consistent hashing). | - Dùng ID số tự tăng nguyên (Auto-increment 1, 2, 3...) của SQLite.<br>- Trùng lặp khóa khi mở rộng sang database phân tán.<br>- Không có bất kỳ mô phỏng nào về giải thuật định danh Chord theo bài học.<br>- Khái niệm Docker DNS bị nhầm lẫn với giải thuật Chord. | - Chưa dùng định danh duy nhất toàn cục (UUID).<br>- Thiếu toàn bộ bài tập lớn về thuật toán Chord theo đúng các số liệu trong slide bài giảng.<br>- Thiếu tài liệu nghiên cứu chuyên sâu về DNS. | - Chuyển toàn bộ ID sang `UUIDv4` chuẩn RFC 4122 cho `userId`, `hotelId`, `roomTypeId`, `bookingId`, `eventId`.<br>- Tách riêng mã tra cứu thân thiện cho khách (`PK-XXXXXX`) với ID khóa chính nội bộ.<br>- Xây dựng module `examples/chord/` mô phỏng đầy đủ vòng Chord $m=6$ (0..63), các node 1, 8, 14, 21, 32, 38, 42, 48, 51, 56, bảng Finger Table tại Node 8, tra cứu khóa có ghi log hop, và minh họa Node 26 tham gia kéo khóa 24 từ Node 32.<br>- Soạn tài liệu hướng dẫn nghiên cứu DNS thực hành tại `docs/dns-study.md`. | - Chạy `tests/chord.test.js` kiểm tra 17 xác nhận toán học khớp 100% slide bài giảng.<br>- Chạy `node examples/chord/chord-cli.js` xem trực tiếp quá trình định tuyến và di chuyển khóa.<br>- Kiểm tra database lưu trữ khóa chính dạng UUID không bị trùng lặp. |
